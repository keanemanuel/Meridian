I found the bug. Waiting on the full test suite. Summary of the investigation so far:

## Root cause

`parse_preferred_dates()` in `src/iff_scheduler/ingest/normalize.py` matched **only full weekday names** (`thursday`, `friday`) via `re.search(r"\bfriday\b", text)`. But this codebase's Applicants tab stores the *short* form that `domain/availability.summarise_availability()` itself renders: `"Thu 17 Sep"`, `"Fri 18 Sep"`, `"Thu 17 Sep; Fri 18 Sep"`. Those cells matched **nothing** → the function returned `{}`.

Downstream, an empty availability trips the `NO_AVAILABILITY` relaxation in `validate.py:279` (`availability = row.availability_slots or list(all_slot_ids)`), which silently fills the applicant in as **available for the entire event**. So:

- **Display (FR-51):** a "Fri 18 Sep" applicant renders with both days.
- **Solver (the serious one — task point 4):** `solver_cpsat.py` reads the same `availability_slots`, so a "Friday only" applicant was genuinely schedulable on Thursday. This was a real scheduling-correctness bug, not just a cosmetic one.

The "collapses to 17" symptom is this fallback: the parser never distinguished 17-only / 18-only / both — every short-form cell became "whole event."

## Fix

`parse_preferred_dates()` now matches **both** the full weekday name (`day.date.strftime("%A")`) **and** the configured short label (`day.label`, e.g. `"Thu"`/`"Fri"`), each on a `\b` word boundary so `"Thu"` doesn't cross-fire on `"Thursday"` and vice-versa. Days not named are left out entirely — no fallback to the first/Thursday day. Removed the now-unused `_WEEKDAYS` constant.

## Tests added (`tests/test_normalize.py`)

- `test_preferred_dates_reads_short_day_labels_without_collapsing_to_thursday` — `"Thu 17 Sep"`, `"Fri 18 Sep"`, `"Thu 17 Sep; Fri 18 Sep"` each resolve to exactly their day(s).
- `test_preferred_dates_short_label_does_not_cross_match_full_name` — boundary check both directions.
- `test_parse_row_short_friday_label_yields_friday_slots_only` — end-to-end via `parse_row`: a `"Fri 18 Sep"` row produces Friday slot IDs only, no Thursday.

Targeted suites (`test_normalize`, `test_availability_summary`, `test_validate`, `test_real_format`) pass (72); ruff + mypy clean. Full `pytest` still running.

## What changed — `src/iff_scheduler/scheduling/feasibility.py`

**1. New `balance_panel_rooms()` pass** — runs at the end of both `rebalance_panels` (after `consolidate_panels`) and `autoscale_panels`.

`_pick_panel_room` fills rooms in config order, so a division that splits several times stacks the first rooms to the ceiling while a room holding only a lone baseline panel is never touched. The new pass repeatedly moves **one load-balanced panel** (`origin == "balanced"` — committed baseline panels never move) from the fullest room that evening to the emptiest, until no room is 2+ panels heavier than another it can shed onto. Every move is skipped if it would break a hard constraint:
- room ceiling — `min(max_concurrent_panels, ROOM_CONCURRENCY_CEILING)`
- room-exclusivity — a division never runs two panels in one room on a day
- room availability — target room open that evening and lists the division

Moved panels get `active_windows` pinned to that evening. The panel *set* is unchanged (only room labels), so capacity/feasibility are untouched. Terminates (each move strictly reduces squared-deviation) and is idempotent.

Now it folds whenever every *other* same-division panel that evening, summed across **all rooms**, can still absorb the whole evening's demand at/under `REBALANCE_THRESHOLD` (85%). The cap-after-removal check is the sole gate, so a genuinely-needed panel stays. Still soft; still never touches a baseline panel; `autoscale_panels` still runs after as the INFEASIBLE backstop. ## Root cause found

**The backend still returns the field; the data behind it went stale.**

2. **Frontend** is also intact — `ApplicantsView.tsx` still renders the `"Preference"` column, and `applicantRows()` in `lib/schedule.ts` still fills it from `a.declared_availability`.

3. **The real regression:** commit `fd2a694 config: shorten event windows — Thu 18:30-21:30, Fri 17:30-21:30` re-timed the grid *after* applicants were ingested. Stored `availability_slots` look like `2026-09-17_1800|_1820|_1840…` (old 18:00 start, 20-min cadence); the current grid emits `2026-09-17_1830|_1850|_1910…`. **Zero slot-ids overlap**, so `summarise_availability()` found nothing on the grid and returned `""` for *every* applicant → the column rendered `·` everywhere and looked "gone." This matches the known "Event window change invalidates availability" issue.

## Fix applied

`src/iff_scheduler/domain/availability.py` — `summarise_availability()` now recovers a **whole-day** preference from a stored slot-id whose exact value has drifted off the grid but whose **date prefix** is still a grid day (the live IFF form collects whole days; only the intra-day granularity is lost, and the ticked date isn't a guess). Exact matches still produce precise time ranges as before; dates not on the grid at all are still ignored.
